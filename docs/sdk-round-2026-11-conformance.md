# Cross-SDK conformance for the 2026-11 SDK fixes

This round of ABsmartly SDK pull requests aligns every SDK to the JavaScript
reference on a set of behaviour changes. This document is the coverage matrix:
one row per wrapper-observable behaviour change, whether a scenario already
covered it, and the scenario id(s) that pin it now. Scenarios live in
`test_scenarios_complete.json` and are generated by
`generate_sdk_round_2026_11_scenarios.py` from the JavaScript reference
(see "Reference / oracle" below).

## Reference / oracle

The JavaScript SDK is the canonical reference. For this round the reference is
**javascript-sdk#67** (`fix/assignment-rules-edge-cases`), which `sdk-branches.sh`
pins for `javascript-sdk`. That branch is:

* `main`, which is already the TypeScript rewrite, already carries custom
  assignment rules (merged from #66), and already registers the `semver_*`
  operators; plus
* the four assignment-rule edge-case fixes of PR #67 (drop a removed
  experiment's rule variant; treat an audience filter that throws as a mismatch;
  parse rules once per data install; stamp system attributes with the earliest
  event and drop user-overridden names).

PR #61 (`worktree-typescript-rewrite`) is a *separate* open rewrite PR; it is 51
commits ahead of `main` and does **not** contain #67's fixes, so it is not the
oracle for this round. The expected results are recorded by
`tools/sdk-round-2026-11/compute.js`, which builds the sibling `../javascript-sdk`
checkout and runs every scenario's steps through it (the generator verifies the
checkout is at the pinned #67 commit before recording anything). The expected
`result` and `events` of every step are the SDK's real output, not hand-written.

## New capabilities

Two `requires` capabilities gate the groups so an SDK that has not implemented
the feature on `main` or any open PR is skipped (a reviewed exception in
`orchestrator/expected-capabilities.json`) rather than failed:

| capability | meaning | advertised by |
| --- | --- | --- |
| `assignmentRules` | custom assignment rules: a matching rule wins with a `ruleOverride:true` exposure and serves variable values | javascript + react/vue2/vue3/angular (behavioral self-test in `assignmentRulesSelfTest.js`), java (`AssignmentRulesSelfTest.java`) |
| `semverOperators` | `semver_eq/gt/gte/lt/lte` audience operators, numeric & locale-independent | same wrappers, same self-tests |

Only **javascript-sdk** (reference) and **java-sdk#17** implement either feature
this round; every other SDK has no implementation on `main` or any open PR
branch (verified across go/php/ruby/python/kotlin/rust/swift/flutter/dart/dotnet/
scala/elixir/cpp/liquid), so each lists both capabilities as a reviewed
exception. When an SDK ports the feature, move the capability from `unsupported`
to `required` for that SDK.

### Reviewed per-SDK exceptions recorded this round

Two further `requires` capabilities encode **owner-approved** behavioural
differences from the JS reference as reviewed per-SDK exceptions, using the same
`orchestrator/expected-capabilities.json` mechanism. They are advertised `true`
by every wrapper that honours the JS behaviour and listed as a reviewed
`unsupported` exception (with reason) only for the SDK the owner exempted, so the
gated scenarios SKIP for that SDK instead of failing. The scenarios themselves
are unchanged.

| capability | meaning | gated scenarios | exempted SDK (reason) |
| --- | --- | --- | --- |
| `numericUnitIds` | a numeric unit uid keeps its numeric JSON type end to end: `getUnit`/`getUnits` return the number the unit was set with (`12345`), not a stringified copy (`"12345"`) | 02, 116, 196, 197 | **php** and **dotnet** — both store unit uids as strings (php: owner decision, Marcio required units be stored as strings for v1.0.3 compatibility; dotnet: the SDK's unit API is string-typed — `SetUnit(string, string)`, `Units` is `Dictionary<string,string>`), so a numeric uid does not round-trip as a number. Neither wrapper re-types the SDK's string back to a number. |
| `publishThrowsOnFailure` | a direct `publish()` whose collector/transport fails surfaces the failure to the caller by throwing; pending events are preserved and an error event is logged | 193 | **php** — php-sdk `publish()`/`flush()` log the collector failure and return instead of throwing (owner decision: Marcio approved logging and returning for v1.0.3 compatibility; only `close()` throws), so a direct `publish()` failure does not surface to the caller |

The **swift** log-instead-of-throw behaviour (scenarios 34, 35, 147, 148, 149,
188, 189, 201) is handled in the swift wrapper rather than as a capability
exception: the swift-sdk public API is intentionally non-throwing (v1.4.0
contract, kept by maintainer decision on swift-sdk#7) and reports misuse (blank
or duplicate unit UID, mutation after finalize, read before ready) through an
`.error` event instead of throwing. The wrapper's `callSurfacingLoggedError`
helper surfaces that logged `.error` as the HTTP error the scenario expects —
matching the JS reference, which throws without emitting an event — so the
scenarios pass unchanged against the real SDK behaviour.

| `refresh()` on a failed context is a no-op | python#11, go#10 | Covered by existing scenario 229 (`readyError`). |
