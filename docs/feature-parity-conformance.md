# Cross-SDK conformance for the 2026-11 feature-parity round

Thirteen SDK PRs port three javascript-sdk features to every SDK, each on its
`feat/assignment-rules-semver-x-agent-publish` branch (java-sdk#22 and the
javascript-sdk#68 reference already had the first two). `sdk-branches.sh` pins
`main` for the SDKs whose PR merged and the PR branch for the rest; see "Branch
pins and merge order" in `docs/sdk-round-2026-11-conformance.md`. This document
lists what scenarios 300-332 pin. They are generated by
`generate_parity_round_scenarios.py`.

## Oracle

The assignment-rules and semver expectations are the real output of
javascript-sdk#68 (`feat/sdk-system-attributes`, commit pinned in
`generate_sdk_round_2026_11_scenarios.py`), run through
`tools/sdk-round-2026-11/compute.js`. Seeds and units for split rules were picked
with the reference `VariantAssigner` so that each pinned variant differs from the
traffic-seed, swapped-seed, zero-seed and normal-split results.

The X-Agent group is the exception: the reference sends the unversioned
`absmartly-javascript-sdk`, so the expectation is the round's contract,
`absmartly-<lang>-sdk/<semver>`, asserted with a regex. `<lang>` must name the
SDK under test and `<semver>` must follow the semver.org 2.0.0 grammar. The
JS-family lanes list `xAgentHeader` as a reviewed exception.

## Reviewed exception found by this group

`semverNumericOperands` gates 332. dotnet-sdk formats a numeric operand with
`G16` (`1e-7` becomes `1E-07`), so the comparison is null where the reference
compares `0.0000001`. That is a dotnet-sdk divergence, listed as a reviewed
exception until dotnet-sdk adopts the reference conversion; every other SDK
passes it.

## Blank client application

Scenarios 322-323 pin `WRAPPER_API_SPEC.md`'s rule that a wrapper forwards an
explicitly supplied `client.application` unchanged and never repairs a blank one
into its own default. SDKs differ on `""`: javascript (and the JS family), cpp,
dart/flutter, dotnet, java, kotlin, rust, scala, swift and ruby/liquid reject it
at client construction, so 322 expects the SDK's own validation error as a 400.
python, go, php and elixir accept it and leave `application` out of the
evaluation map, so 323 expects an `application`-present audience to miss while
the configured environment still matches. Each SDK requires exactly one of the
two capabilities. A wrapper that substitutes its default fails either one. The
JS reference rejects `""`, so 323's expectations follow the system-attributes
contract (scenario 253's absence check) instead of a reference run.

## Harness support

`capturedRequests` reads the requests a wrapper's mock collector recorded
(`GET /context_payload/{id}/requests`), and `createContext` forwards
`publishToEndpoint` so the SDK publishes through its own HTTP client to
`PUT {endpoint}/context`. See WRAPPER_API_SPEC.md section 2b-i.

## Generators

`generate_sdk_round_2026_11_scenarios.py` owns 230-253 and
`generate_parity_round_scenarios.py` owns 300-332; both read their group markers
from `scenario_groups.py`. Each regenerates only its own groups and leaves the
other's where they are, so both `--check` runs pass on the same file (pinned by
`ScenarioGeneratorsCoexistTest` in `tests/test_harness.py`).

`--check` needs the pinned javascript-sdk build, so CI does not run it. Instead
`orchestrator/tests/test_parity_scenarios.py` digests 300-332 (as
`test_system_attributes_scenarios.py`'s `KEPT_DIGEST` does for the rest): a hand
edit to any parity scenario fails CI. Update the digest only together with a
regeneration whose `--check` is clean.
